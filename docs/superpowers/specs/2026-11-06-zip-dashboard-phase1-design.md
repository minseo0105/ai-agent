# ZIP 대시보드 1단계 설계 — 지도 대시보드 · 8단계 타임라인 · 투자금 시뮬레이터

작성일 2026-11-06 · 상태: **조건부 승인(2026-11-06) — 보완사항 6개 반영본** · 선행 문서: `docs/zipon_platform_diagnosis_2026-11-06.md`

## 1. 이해한 요구사항

**목표.** 사용자가 지도에서 개발구역을 고르면 한 화면에서 사업 단계, 거래 전 확인사항, 예상 투자금을 본다.

**이번 범위(하위 프로젝트 1).** 대시보드 레이아웃, 8단계 타임라인, 거래 전 체크포인트, 투자금 시뮬레이터, 4개 탭 구조.

**지킬 것(사용자 지정).** 기존 1,190건의 검색·필터·마커 유지 / 기존 DB 구조 유지 / 운영 DB 변경·배포는 별도 승인 / 실제 데이터가 없는 곳에 임의 값 표시 금지 / 검증된 Polygon이 없으면 마커 유지 / 법적 거래 가능 여부를 확정적으로 판정하지 않음 / 경계 활성화(2)와 실거래 연동(3)을 위해 화면 재설계가 필요 없는 구조.

**이번 범위 밖.** 실거래 조회·매칭, 사전진단 엔진, 구역 비교, 관심 구역·알림, 매물 연동, 경계 활성화.

## 2. 화면 구성

### 데스크톱 (1024px 이상) — 지도 65% · 패널 35%

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ ZIP   [ 지역·주소·사업명 검색 ........................ ]   서울 25개구 ▾   │
│ (전체 1,190) 재개발 · 재건축 · 신속통합기획 · 모아타운 · 기타   단계 ▾  ☐완료 │
├───────────────────────────────────────────────┬─────────────────────────────┤
│  (65%)  지도                                  │  (35%)  패널                │
│                                               │  ── 아무것도 안 골랐을 때 ──│
│    ● ● 클러스터(14)      ●                    │  목록 N건 (지도 범위/필터)  │
│        ●        ● 선택됨(크게)                │  ┌ 사업명  유형·단계 ──────┐│
│   ●                 ▢ 검증된 경계(있을 때만)  │  │ 구  ·  갱신 N일 전      ││
│                                               │  └─────────────────────────┘│
│  [범례]  [데이터 기준일 · 출처]               │  ── 골랐을 때 ───────────── │
│  ⚠ 마지막 공식 확인 N일 전 (오래된 경우만)    │  ← 목록  사업명   ☆(추후)   │
│                                               │  [사업정보][실거래][투자분석]│
│                                               │  [거래가이드]               │
└───────────────────────────────────────────────┴─────────────────────────────┘
```

- 마커·목록 클릭은 **양방향**: 마커 → 패널 열림 + 목록 스크롤, 목록/패널 → 지도 이동·선택 강조. 선택 상태는 하나(`selectedId`)이고 URL 해시(`#zone=<id>`)에 반영해 새로고침·링크 공유 때 복원한다.
- 패널은 `Esc`와 "← 목록" 버튼으로 닫는다. 패널이 열려도 필터·검색은 그대로 유지된다.

### 모바일·태블릿 (1024px 미만) — 지도 위 바텀시트

```
┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
│ 검색 · 필터 칩      │   │ 검색 · 필터 칩      │   │  ▬▬  (시트 확장)    │
│                     │   │      ●  ●           │   │ 사업명        ✕     │
│        지도         │   │   ●  선택됨 ●       │   │ [정보][실거래]...   │
│   ●   ●      ●      │   ├─────────────────────┤   │ 내용 …              │
│                     │   │ ▬▬ 사업명 · 단계    │   │                     │
│  [목록 보기]        │   │ [정보][실거래]…     │   │                     │

- 시트는 peek / full 두 단계, 헤더의 손잡이 버튼과 위·아래 스와이프로 전환(터치 이벤트는 자체 구현, 라이브러리 추가 없음). 선택하면 peek로 열린다.
- 목록 보기는 같은 시트의 "목록 모드"다. 지도는 뒤에서 계속 보인다.

| 탭 | 지금 내용 | 나중에(2·3) |

## 3. 사업 단계 타임라인

### 3-1. 원칙: 공식 정보가 항상 우선한다

화면의 8단계는 **안내용 요약**이고, 서울시 정비사업 정보몽땅의 공식 단계·날짜가 원본이다. 둘이 일치하지 않으면 다음 규칙을 따른다.

| 상황 | 표시 |
|---|---|
| 공식 단계에 날짜가 있음 | 안내용 흐름과 무관하게 **도달(일자 확인)** + 공식 날짜. 예: 재개발인데 안전진단 날짜가 공식 기록에 있으면 그대로 표시 |
| 공식 현재 단계가 8단계 밖(기본계획수립·안전진단·일반분양승인·조합해산·조합청산) | 8단계 막대 밖의 **보조 줄**에 공식 이름 그대로 표시하고 "현재(공식)" 배지를 붙임. 8단계 진행 문구는 공식 날짜가 확인된 단계만 근거로 계산 |
| 공식 데이터에 없는 단계 | `기록 없음`. 안내용 흐름이 "거치는 단계"라고 말하더라도 도달로 추정하지 않음(위 "지난 단계" 규칙의 경우만 예외) |
| 안내용 흐름이 "일반적으로 거치지 않음"이라고 한 단계 | 공식 기록이 없으면 `일반적으로 거치지 않는 단계`(회색 보조 표시), 공식 기록이 있으면 위 첫 행이 우선 |
| 공식 상세를 확인하지 못한 사업(목록 정보만) | 8단계를 그리지 않고 공식 현재 단계 한 줄과 "공식 상세 확인 전" 안내 |

### 3-3. 유형별 흐름 규칙(안내용)

| 유형 코드 | 흐름 | 화면 문구 |
|---|---|---|
| `REDEVELOPMENT` 재개발 | 안전진단 제외 | "재개발은 일반적으로 안전진단을 거치지 않습니다. 공식 기록이 있으면 표시합니다." |
| `RECONSTRUCTION` 재건축 | 안전진단 포함(사전 단계) | "재건축은 안전진단이 사전 단계입니다." |
| 그 밖(`MOATOWN`·`MOAHOUSE`·`SHINTONG`·`FAST_TRACK`·기타) | **별도 흐름을 정의하지 않음** | "이 유형의 별도 절차는 정의하지 않았습니다. 공식 단계 이름을 그대로 표시합니다." — 어떤 단계도 `해당 없음`으로 표시하지 않음 |
| 신속통합기획·모아타운 | 사업 유형이 아니라 **정책 프로그램**(기존 `program` 분리 정책 유지) | 프로그램 배지만 표시, 흐름은 기본 유형을 따름 |

이 차이는 **우리가 정의한 안내 규칙**이며 법 해석이나 공식 사실이 아니다. 화면에 항상 그렇게 표시한다.

### 3-4. 단계 상태

| 상태 | 조건 | 표시 |
|---|---|---|
| **현재 단계** | 공식 현재 단계가 이 화면 단계에 속함 | 채운 원 + "현재" |
| **도달(일자 확인)** | 공식 날짜 있음(현재 단계 이전·이후 불문, §3-1) | 체크 + 날짜(원문, 정밀도 표기) |
| **지난 단계(일자 미공개)** | 공식 현재 단계가 이 단계보다 뒤인데 날짜가 없고, 안내용 흐름이 거치는 단계 | 반쯤 채운 표시 + "일자 미공개" |
| **예정** | 공식 현재 단계가 이 단계보다 앞 | 빈 원 |
| **기록 없음** | 현재 단계가 보조 줄(8단계 밖)이어서 이 단계의 위치를 판단할 수 없고 날짜도 없음 | 회색 `기록 없음` |
| **공식 상세 미확인** | 목록 정보만 있음 | 8단계 미표시 |

공식 현재 단계는 "그 인가를 받은 상태"를 뜻하므로 현재 단계까지를 "도달"로 센다. 준공·이전고시(8단계)는 하위 2개 중 하나라도 공식 단계에 도달하면 현재, 둘 다 날짜가 있으면 도달(일자 확인).

### 3-5. 진행 표기

임의의 백분율은 쓰지 않는다. **"8개 주요 단계 중 4단계 도달 (일자 확인 3)"** 형식이다. 공식 현재 단계가 조합해산·조합청산이면 진행 문구 대신 "사업 종료 기록(해산·청산) — 완료 여부는 공식 자료로 확인 필요"를 표시한다. 목록 정보만 있는 사업은 진행 문구를 표시하지 않는다.

### 3-6. 각 단계에 표시하는 항목

단계명 · 상태 · 실제 인가·고시일(원문, 정밀도) · 주요 의미 · 다음 단계 · 공식 출처 링크(사업 상세 페이지 하나. 단계별 문서 링크는 **제공되지 않음**) · 거래·권리 확인 질문(§4, 질문형). 향후 일정은 표시하지 않는다(공식 일정 없음).

## 4. 거래 전 체크포인트 카드

- 내용: 현재 단계에서 확인할 항목 3~5개(기존 `stage_guide.checks` + `investor_guide.watch_next` 재사용), "다음 단계에서 달라지는 점", "이 사업에서 확인된 값이 아니라 일반 안내"라는 문구, 면책.
- 표현은 **질문형**이다("조합원 지위 승계가 가능한지 확인"). "거래 가능/불가" 같은 단정 문구는 쓰지 않는다. 규제·예외 조문을 인용하는 문구는 법령 검증이 끝나는 하위 프로젝트 4에서 추가한다.

## 5. 투자금 시뮬레이터

### 입력(모두 사용자 입력, 기본값 없음)

매입가격 · 종전자산 감정평가액 · 비례율(%) · 조합원 분양가 · 취득 관련 비용(합계) · 대출금액 · 금리(연 %) · 보유기간(개월) · 기타 비용 · 가정 준공 후 시세. 단위는 만원이다.

### 항목 관계 정의 (화면에 그대로 표시, 사용자가 확인)

기호: 매입가격 P · 종전자산 감정평가액 A · 비례율 r(%) · 조합원 분양가 S · 취득 관련 비용 C · 대출금액 L · 금리 i(연 %) · 보유기간 m(개월) · 기타 비용 E · 가정 준공 후 시세 V.

```
권리가액 R   = A × r/100                       ← 이 매물이 조합에서 인정받는 금액(참고값)
추가분담금 X = S − R                           ← 부호 있음. 양수=추가 납부, 음수=환급 예상
금융비용 F   = L × i/100 × m/12               (단순 이자, 분할상환·복리 미반영)
총투자금 T   = P + C + X + F + E
자기자본 Q   = T − L
가정 손익 G  = V − T
가정 수익률  = G ÷ Q                           (Q ≤ 0이면 계산하지 않음)
```

**중복 계산 방지 규칙(테스트로 고정):**
1. **권리가액 R은 총투자금에 더하지 않는다.** R은 추가분담금 X를 구하는 데만 쓴다. 매입가격 P는 이미 그 권리를 사는 대가이기 때문이다. 이 두 값을 둘 다 더하면 같은 금액을 이중으로 세게 된다.
2. 추가분담금 X는 **한 번만, 부호 그대로** 더한다. 환급(X<0)은 별도로 빼지 않는다(`T = P + C + X + F + E`에서 X가 음수라서 이미 차감됨). 화면에는 "추가 납부 X원" / "환급 예상 X원"을 구분해 보여주되 합계에는 한 번만 반영한다.
3. 금융비용 F는 `T`에 한 번만 포함한다. 자기자본 Q = T − L이므로 대출 원금은 Q에서 빠지고, 이자 F는 T에 들어 있어 Q에도 반영된다.
4. 취득 관련 비용 C는 매입가격 P와 **별개 입력**이다(P에 포함해서 넣지 않도록 입력 설명에 명시).
5. 가정 준공 후 시세 V는 손익 계산에만 쓰며 T에 들어가지 않는다.

**관계 검증식(단위 테스트):** `T − (P + C + F + E) = X` / `R`이 변해도 `T`는 오직 `X`를 통해서만 변함(`ΔT = −ΔR`) / `S = R`이면 `X = 0`이고 `T = P + C + F + E` / `V = T`이면 `G = 0`.

### 시나리오

기준 / 보수 / 낙관 3열을 나란히 비교한다. 보수·낙관은 기준 입력에 **조정폭**을 적용해 같은 계산식으로 계산하고(시나리오마다 다른 식을 쓰지 않음), 조정폭은 화면에서 수정·초기화할 수 있다. 적용 방식: 비례율 `r + Δ(%p)`, 분양가 `S × (1 + Δ/100)`, 가정 시세 `V × (1 + Δ/100)`, 보유기간 `max(0, m + Δ)`, 금리 `max(0, i + Δ)`. 매입가격·감정평가액·비용·대출은 시나리오와 무관하게 고정.

| 조정 항목 | 보수 기본 | 낙관 기본 |
|---|---|---|
| 비례율 | −5%p | +5%p |
| 조합원 분양가 | +5% | −3% |
| 가정 준공 후 시세 | −10% | +10% |
| 보유기간 | +12개월 | −6개월 |
| 금리 | +1%p | −0.5%p |

이 기본 조정폭은 **예시 가정이며 사실이 아님**을 화면에 명시한다(수정 가능, 초기화 버튼 제공).

### 입력 검증과 특수 상황

- 필수 입력(감정평가액·비례율·분양가)이 없으면 권리가액·분담금 칸은 `입력 필요`로 두고 값을 만들지 않는다. 선택 입력이 비면 0으로 계산하되 "미입력 항목: …"을 결과 위에 표시한다.
- 비례율이 일반적인 범위를 크게 벗어나면(예: 0 이하 또는 200% 초과) 계산은 하되 "입력값 확인" 경고를 표시한다.
- 추가분담금이 음수(환급), 0, 양수 세 경우의 문구를 구분한다. 확정 수익이 아니라 가정 기반 추정치임을 결과 영역에 항상 표시한다.
- 입력값은 사업별로 브라우저(`localStorage`)에 저장한다. 접근 실패 시에도 화면은 정상 동작한다.

목록 응답(1,190건)은 커지지 않는다. 상세는 구역을 골랐을 때만 1건씩 조회한다. 실패하면 목록 데이터만으로 요약을 보여주고 상세 영역에 오류를 표시한다.

### `connections` — 실제 서버 상태를 기준으로 계산한다

화면이 상태를 하드코딩하지 않는다. 서버가 **요청 시점의 실제 설정·데이터**에서 계산한다. 구현되지 않은 기능은 어떤 상태값으로도 "사용 가능"을 말하지 않는다.

```
connections: {
  trades: {
    state: "REGIONAL_ONLY" | "NOT_CONNECTED",
        // NOT_CONNECTED: 국토부 API 키가 서버에 없음(rm.get_api_status().public_data_key == false)
        // REGIONAL_ONLY: 키가 있어 기존 '실거래 조회' 탭(자치구·월 단위)은 가능. 구역 패널 연동은 아님
    api_key_configured: bool,                    // 실제 서버 설정에서 읽음
    linked_types:  ["아파트","연립·다세대","단독·다가구","오피스텔"],  // rm.TRADE_APIS 키에서 읽음
    unlinked_types: ["토지"],                    // 구역 대상 유형 중 TRADE_APIS에 없는 것
    zone_panel: "NOT_IMPLEMENTED",               // 코드가 실제로 구현된 때만 바뀜
    zone_matching: "BLOCKED_NO_VERIFIED_BOUNDARY" | "NOT_IMPLEMENTED",
        // 이 사업의 경계가 검증되지 않았으면 BLOCKED, 검증됐더라도 구역 패널이 미구현이면 NOT_IMPLEMENTED
    coordinate_provider_configured: bool         // 지오코더 키 실제 설정 여부
  },
  rights_engine: { state: "NOT_CONNECTED" },     // 엔진 코드가 없으므로 항상 NOT_CONNECTED

각 값은 서버 설정·상수·해당 사업의 `geometry_verified`에서 계산하고, 기능이 구현될 때 **그 기능을 만드는 변경이 이 계산도 함께 바꾼다**(별도의 "사용 가능" 플래그를 두지 않음). 테스트: 키 없음/있음, 경계 검증 여부, 상태값이 구현 여부와 모순되지 않는지.

### 7-1. 마커 클러스터링 결정 기록 (조건 3)

**조사한 것.** NAVER 지도 v3는 SDK 본체에 클러스터링을 두지 않고, 공식 예제 저장소 `navermaps/marker-tools.js`의 `MarkerClustering.js`(Apache-2.0, 745줄)를 내려받아 쓰도록 안내한다. 이 파일을 직접 내려받아 읽고 확인했다.

| 확인 사항 | 결과 |
|---|---|
| 배포 형태 | npm 패키지 아님, 저장소 파일. 가져다 쓰려면 파일을 프로젝트에 넣어야 함 |
| 라이선스 | 파일 머리글에 Apache-2.0(Copyright 2016 NAVER Corp.). 저장소 화면에는 별도 LICENSE 파일 표시가 없음 |
| 결함 ① | `onAdd`는 `_mapRelations`에 `idle` 리스너를 저장하는데 `onRemove`는 존재하지 않는 `_mapRelation`을 해제 → 지도에서 떼어도 리스너가 남음 |
| 결함 ② | `changed()`는 키 `'marker'`를 처리하지만 옵션 키는 `'markers'` → 연결된 상태에서 `setMarkers`가 다시 그리지 않음 |
| 결함 ③ | `averageCenter`는 `markers[i].position.x/.y`를 읽는데 NAVER Marker는 위치를 `getPosition()`으로 노출 → 켜면 값이 틀릴 수 있음 |
| 구조 | 지도 `idle` 때마다 전체 클러스터를 삭제 후 재생성. 공간 색인 없이 마커마다 모든 클러스터를 검사 |
| 우리 요구와의 차이 | 마커 객체(`naver.maps.Marker`)를 직접 받아 보이기/숨기기를 제어함. 우리 지도는 사업별 아이콘·선택 강조·필터에 따라 마커를 갱신하고, **선택한 구역은 항상 개별 마커로 보여야 하며** 클러스터에 숨으면 안 됨 |

**결정: 클러스터 *계산*은 순수 함수로 자체 구현하고, 그 결과를 기존 마커 파이프라인(`naver.maps.Marker`)으로 그린다.**

**자체 구현이 불가피한 이유.** (1) 공식 구현은 SDK 기능이 아니라 예제 파일이며 위 결함 3개가 코드에서 확인됐다. 가져다 쓰면 결함을 고친 복제본을 우리가 유지해야 한다. (2) 우리 지도는 필터·선택에 따라 마커를 갱신하고 선택 구역을 클러스터에서 제외해야 하는데, 공식 구현은 마커 가시성을 자체 제어해 이 요구와 충돌한다. (3) NAVER SDK는 이 샌드박스에서 접속할 수 없어 공식 구현을 실제로 붙여 검증할 수 없지만, 순수 함수는 지도 없이 정확성·성능을 테스트할 수 있다.

**자체 구현 방식.** 공식 옵션 이름(`gridSize`·`minClusterSize`·`maxZoom`)을 그대로 따른다. 웹 메르카토르 픽셀 좌표를 줌 수준에서 계산해 `gridSize`(기본 64px) 격자 칸에 해싱하는 **O(n) 격자 방식**이다. 칸 안의 점이 `minClusterSize`(2) 이상이면 클러스터, 클러스터 위치는 구성원의 평균 좌표, `maxZoom`(기본 14) 이상에서는 클러스터링하지 않는다. 선택한 사업은 클러스터에서 빼고 항상 개별 마커로 둔다. 클러스터 클릭은 해당 구성원이 모두 보이는 범위로 확대한다. 좌표가 없는 사업은 처음부터 마커 대상이 아니다(기존 동작 유지).

**성능·정확성 테스트(필수).** 정확성: 모든 점은 정확히 한 그룹에 속함(합계 = 전체) / 동일 좌표는 한 클러스터 / 줌이 커질수록 그룹 수가 줄지 않음 / `maxZoom` 이상에서 클러스터 0개 / 선택 사업 제외 / 결정적 결과(같은 입력·같은 출력) / 클러스터 중심이 구성원 경계 상자 안. 성능: 1,190점 < 20ms, 10,000점 < 150ms 목표(실측 후 기준 확정, 기준 초과 시 실패).

**확장 자리(구현은 안 함, 타입과 props만):**
- 경계: `ZiponMap`은 이미 `point.boundary`가 검증되면 Polygon을 그린다. 2단계 후 데이터가 채워지면 코드 변경 없이 표시된다. 단계별 색은 지금 마커 색 체계를 Polygon 채움에도 사용.
- 실거래: `ZiponMap`에 선택적 `tradeMarkers` prop(없으면 아무것도 안 그림), `TradesTab`에 `trades?: ZoneTrade[]`. `ZoneTrade.zone_relation`은 `INSIDE_CONFIRMED | NEARBY_ESTIMATED | UNKNOWN`(요구사항의 3분류).
- 권리: `RightsAssessment`는 결과 `NO_LIMITATION_FOUND | NEEDS_CHECK | LEGAL_RISK`, 근거·법령·기준일·부족한 정보 필드를 가진다. 엔진이 없는 지금은 아무것도 판정하지 않는다.

## 8. 디자인 방향

- 흰 배경, 단일 브랜드 포인트 컬러(**퍼플**)를 새 토큰으로 추가(`--zip`, `--zip-soft`). 다크모드 값도 정의. 다른 서비스 색은 건드리지 않음.
- 숫자·상태 위계: 큰 숫자(권리가액·총투자금), 상태 칩, 출처·기준일은 작은 보조 텍스트.
- 패널 전환: 선택 시 목록 → 상세 슬라이드(150ms), `prefers-reduced-motion`이면 즉시 전환.
- 접근성: 탭은 `role="tablist"`, 방향키 이동, 지도 위 모든 조작에 키보드 대안(목록).
