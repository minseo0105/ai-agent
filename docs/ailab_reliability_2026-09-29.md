# AI LAB 안정성 · 상태 정확성 (2026-09-29)

## 무엇이 문제였나

| 증상 | 실제 원인 |
| --- | --- |
| "FastAPI 서버에 연결하지 못했습니다" | 컨테이너가 깨어나는 동안 첫 요청이 실패한다. 화면은 그것을 영구 장애로 말했고, 다시 시도하지 않았다. |
| 큰 500 화면 | 처리되지 않은 예외를 받는 곳이 없었다. 프레임워크 기본 응답이 그대로 나갔다. |
| 원인 추적 불가 | 요청에 id가 없고 접근 로그가 없었다. 어떤 요청이 왜 실패했는지 뒤에서 알 수 없었다. |
| 조건을 바꿔도 결과가 그대로 | 검색 요청에 번호도 취소도 없었다. 먼저 보낸 느린 응답이 나중에 도착해 새 결과를 덮어썼다. |
| 로딩 중 이전 결과가 보임 | 새 검색이 시작될 때 이전 결과를 지우지 않았다. |
| 지도에 끝난 사업이 섞임 | 생애주기가 화면까지 오지 않았다. |

## 공통으로 고친 것

**요청 추적** — `api/reliability.py`. 요청마다 id를 붙여 `X-Request-Id` 헤더와 로그에 같은 값을
남긴다. 로그 한 줄에 `method · path · status · duration_ms · request_id`가 들어간다.
`Authorization`·`apikey`·`serviceKey`·`Cookie`·`password` 같은 이름이 든 값은 `***`로 지운다.

**오류 응답** — 처리되지 않은 예외는 500 JSON 하나로 바뀐다. traceback은 서버 로그에만 남고
화면에는 안내문과 `request_id`만 간다. 오류를 200으로 숨기지 않는다. 의도한 `HTTPException`은
원래 메시지와 상태 코드를 그대로 유지한다.

**상태 점검** — `/api/health`는 프로세스만 본다. 바깥으로 아무것도 부르지 않고 바로 답한다.
헬스체크가 외부를 호출하면 남의 장애로 이 프로세스가 재시작된다. 의존성 상태는 `/api/ready`에
따로 있고, 점검은 서로 격리되어 하나가 예외를 던져도 나머지는 그대로 확인된다.
필수(`supabase`)가 죽어야 `not_ready`이고, 부가 의존성 장애는 `degraded`일 뿐이다.
실패 사유는 예외 **종류만** 남긴다(주소·자격증명이 담긴 메시지를 내보내지 않는다).

**cold start** — `api.main` 적재 시간 **2558ms → 708ms**. 모델 SDK(`anthropic`, `openai`)와
렌더 라이브러리(`matplotlib`, `reportlab`)를 실제로 쓸 때 불러오도록 옮겼다. 골프·부동산 요청은
이제 그 비용을 내지 않는다(테스트가 이를 고정한다).

**프론트엔드 요청** — `apiFetch`에 시간제한(기본 20초, 검색 45초)과 취소(`AbortSignal`)를 넣었다.
시간제한이 없으면 화면이 영영 로딩에 머무르고, 취소가 없으면 지난 응답이 최신 결과를 덮어쓴다.
`web/src/lib/coldStart.ts`는 **읽기 요청만** 0.7초·1.5초·3초 간격으로 다시 시도한다.
쓰기 요청은 같은 일이 두 번 일어날 수 있으므로 자동 재시도하지 않는다.
다시 시도하는 실패는 연결 실패와 502/503/504뿐이다.

## Golf

**최신 요청만 이깁니다.** 검색마다 번호를 매기고(`generation`) 새 검색이 이전 검색을
취소한다(`AbortController`). 응답이 도착해도 자기 번호가 최신이 아니면 화면을 건드리지 않는다.
로딩 해제도 최신 검색만 한다. 모드 전환도 진행 중인 검색을 끊는다.
조건이 바뀌면 이전 결과를 먼저 지운다. 취소된 요청은 오류로 표시하지 않는다.

**거리순은 실제 거리값 순서다.** 직선거리로 전체를 정렬하고, 상위 20곳만 실주행 거리를 조회해
그 값으로 다시 정렬한다. 좌표가 없는 골프장은 맨 뒤로 간다(위로 올라오지 않는다).
출발지 좌표를 찾지 못하면 거리순이라고 말하지 않고 안내문을 띄운다.
정렬은 화면이 목록을 자르기 전에 끝난다. 화면은 거른 뒤에 자른다.

**캐시 키**는 인자 전체다. 지오코딩은 질의어로, 경로는 출발·도착 좌표 네 개 모두로 구분된다.

## ZIP:ON

**생애주기는 이미 있던 공식 규칙을 화면까지 연결한 것이다.** 새 판정 규칙을 만들지 않았다.
`STATUS_FROM_STAGE`가 준공인가·이전고시만 COMPLETED로 본다. 착공은 완료가 아니다.
조합해산·청산은 끝났을 수 있다는 가설만 적고 UNKNOWN으로 둔다.
사업명이나 오래됐다는 이유로 완료라고 하지 않는다.

기본 지도는 `ACTIVE · CONSTRUCTION · UNKNOWN`을 그리고 `COMPLETED · CANCELLED`를 뺀다.
**UNKNOWN은 숨기지 않는다.** 확인하지 못한 것을 끝난 것으로 다루면 진행 중인 사업이 조용히
사라진다. `[완료사업 보기]`는 기본 꺼짐이고, 켜면 완료 사업이 그대로 돌아온다.
DB에서 지우지 않는다. 숨길 뿐이다.

130건 감사 결과는 `data/development/lifecycle_audit_20260929.json`에 있다.

| 구분 | 건수 |
| --- | ---: |
| COMPLETED (공식 종결 단계) | 19 |
| CONSTRUCTION (착공) | 4 |
| UNKNOWN | 107 |
| REVIEW_REQUIRED (해산·청산 가설) | 37 |
| 기본 지도에서 빠지는 건 | 19 |

`ACTIVE`와 `CANCELLED`로 확정된 건은 없다. 공식 근거가 그것을 말해 주지 않기 때문이다.

**공간 안전 규칙은 그대로다.** 대표좌표만으로는 INSIDE가 되지 않고, 확인된 공식 경계만
INSIDE를 만든다. 생애주기 판정은 identity·좌표·경계·단계 이력을 건드리지 않는다.
`seoul-identity-v1`은 그대로다.

## 하지 않은 것

- 대규모 리팩터링. 실제로 안정성이 나아지는 곳만 고쳤다.
- production DB write. 생애주기 130건은 검토 산출물까지만이다.
- RLS·권한·키 취급 변경.
- 오래된 golf 테스트(Streamlit 페이지 대상) 수정. 이번 변경과 무관하게 이전부터 실패 중이다.

## production 반영이 필요해지면

지금은 필요하지 않다. 나중에 생애주기를 DB에 적을 때는 폴리곤과 같은 순서를 따른다:
`dry-run → canary(1건) → reconciliation(다시 읽어 확인) → apply`.
