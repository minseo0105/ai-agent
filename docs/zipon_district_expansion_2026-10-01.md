# ZIP:ON 개발정보 수집범위 — 서울 25개 자치구 확대 (dry-run, 2026-10-01)

Production Supabase에 쓴 것은 없습니다. 이 문서와 함께 들어온 변경은 수집 **범위를
선택할 수 있게** 만든 것과, 좌표를 채택하기 전에 자치구 일치를 확인하게 만든 것,
그리고 데이터가 없는 자치구의 화면 문구입니다.

## 1. 지역 마스터 — 새 사전을 만들지 않았습니다

서울 25개 자치구 코드는 `services/realestate_monitor.py`의 `REGION_LAWD` 하나에서만
옵니다. `development_collector`는 그중 `서울 > `로 시작하는 25개를 읽어
`SEOUL_SIGNGU_CODE`로 펼칩니다.

```
SIGNGU_CODE_SOURCE = 'services.realestate_monitor.REGION_LAWD'
SEOUL_SIGNGU_CODE  = {'종로구': '11110', ... , '강동구': '11740'}   # 25개
```

재사용 전에 두 코드가 같은 체계인지 확인했습니다.

| 자치구 | 실거래 `LAWD_CD` | 정보몽땅 `signguCode` | 결과 |
|---|---|---|---|
| 강동구 | 11740 | 11740 | 일치 (적재 데이터로 확인) |
| 송파구 | 11710 | 11710 | 일치 (적재 데이터로 확인) |
| 서초구 | 11650 | 11650 | 일치 (적재 데이터로 확인) |

양쪽 모두 행정표준코드 시군구코드 5자리이고, 서울 25개는 전부 `11xxx`이며 중복이
없습니다(테스트 `RegionMasterTests`). **다만 실제 정보몽땅 응답으로 검증된 것은 위
세 개뿐입니다.** 나머지 22개는 코드 체계가 같다는 것까지만 확인된 상태이므로, 망이
열린 환경에서 구별 응답 건수를 확인한 뒤에 적재해야 합니다.

`DISTRICTS`(기존 세 구 하드코딩)는 제거하지 않고 **기본값**으로 남겨 두었습니다.
값이 25개로 바뀐 것이 아니라, 25개 중 세 개를 가리키는 파생값이 되었습니다.

## 2. 수집 범위 선택

```
python scripts/collect_zipon_pilot.py                          # 기존 세 구 (기본값, 동작 불변)
python scripts/collect_zipon_pilot.py --district 성동구
python scripts/collect_zipon_pilot.py --districts 성동구,마포구,용산구
python scripts/collect_zipon_pilot.py --all-seoul
```

- 25개를 무조건 매번 도는 경로는 없습니다. `--all-seoul`을 쓸 때만 25개입니다.
- 모르는 이름은 조용히 건너뛰지 않고 거부합니다. 오타 하나가 "그 구는 수집된 게
  없다"로 보이는 것이 가장 나쁜 실패 방식입니다.
- `하남시` / `경기 > 하남시`도 거부합니다. 경기는 이 수집기의 범위가 아닙니다(8항).
- 전부 실패한 수집으로 기존 캡처 파일을 덮지 않습니다.

구조상 범위가 걸려 있던 곳은 두 군데였고 둘 다 선택값을 따릅니다.

1. 구별 사업장 목록 URL(`scupBsnsSttus.signguCode=`) — 선택한 구만큼 만듭니다.
2. `parse_page`의 행 필터 — 시 전체 페이지(모아타운·신속통합기획)는 원래 25개 구 행을
   모두 돌려주는데 세 구가 아닌 행이 전부 버려지고 있었습니다. 이제 source가 들고 있는
   범위로 고릅니다.

## 3~4. Dry-run과 품질

`scripts/dryrun_zipon_districts.py`가 수집 → 정규화 → 중복제거 → geocoding →
유형분류 → identity → 기존 DB 중복 → insert/update 예상까지 한 번에 냅니다.
Supabase write 경로를 import하지 않습니다.

**입력 모드가 결과의 성격을 결정합니다.**

| 모드 | 무엇 | 숫자의 성격 |
|---|---|---|
| `--live` | 공식 페이지를 실제 수집 | 공식 실적 |
| `--replay <artifact>` | 캡처된 `field_evidence.cells`로 공식 표를 복원해 재파싱 | 실데이터 |
| (기본) fixture | 열 구성만 같고 행 내용은 합성 | **파이프라인 동작 확인용. 공식 건수 아님** |

이 컨테이너의 egress 정책이 `cleanup.seoul.go.kr`와 `news.seoul.go.kr`를 막고
있어(`ProxyError`, HTTP 000) 성동·마포·용산의 `--live` 수집은 실행하지 못했습니다.
그래서 신규 3개 구는 fixture 모드 결과이고, artifact에 `synthetic_rows: true`로
표시됩니다. 공식 건수로 인용해서는 안 됩니다.

산출물:
- `data/development/district_expansion_dryrun_20261001.json` (성동·마포·용산, fixture)
- `data/development/district_expansion_regression_20261001.json` (서초·송파·강동, 실데이터 재생)

### 서울 25개 전체 수집 규모 — 추정이며 실측이 아닙니다

측정된 것은 세 구뿐입니다(서초 72 / 강동 59 / 송파 52 = 183행). 두 종류를 나눠
보아야 합니다.

| 출처 | 세 구 실측 | 25개 구 확대 시 |
|---|---|---|
| 구별 사업장 목록 (정보몽땅, 구별 URL) | 149행 (47+40+62) | 구마다 요청이 하나씩 늘어남. 산술 환산 약 1,240행 |
| 시 전체 페이지 (신속통합기획 재개발 7 / 재건축 27) | 34행 | 요청 수는 그대로. **이미 받고 있던 응답에서 버려지던 행이 살아남을 뿐** |
| 모아타운 (시 전체) | 0행 (캡처 당시 ConnectTimeout) | 미측정 |

구별 사업장 목록의 약 1,240행은 `183 / 3 × 25`가 아니라 `149 / 3 × 25`입니다.
그리고 이 세 구는 재건축·재개발이 많은 구이므로 **과대추정일 가능성이 높습니다.**
그래서 이 숫자는 "요청이 6건에서 28건으로 늘어난다"는 규모 감각 외에는 쓰지 말고,
망이 열린 환경에서 `--all-seoul --live` 한 번으로 실측해야 합니다.

확실한 것: 요청 수는 6건 → 28건(시 전체 3 + 구별 25)이 되고, 구별 사업장 목록은
`pageSize=100` 단일 페이지 요청이라 100행을 넘는 구는 `PARTIAL`로 남습니다.
페이지네이션은 이번 변경 범위가 아니며, 지금도 `PARTIAL`은 누락이지 폐지가 아닙니다.

## 5. 지도 검증 — 서울 bbox만으로는 통과하지 못합니다

`development_collector.geocode`가 좌표를 채택하는 조건이 늘었습니다.

| 검사 | 거부 사유 코드 |
|---|---|
| MATCHED / accuracy BUILDING·PARCEL / source_url | `NOT_MATCHED` · `ACCURACY_NOT_EXACT` · `NO_SOURCE_URL` |
| 한반도 범위 (축 뒤집힘 탐지) | `OUTSIDE_KOREA_BBOX` |
| 서울 bbox | `OUTSIDE_SEOUL_BBOX` |
| 사업 `sigungu` == 응답 자치구 | `GEOCODE_SIGUNGU_MISMATCH` |
| 응답에서 자치구를 읽을 수 없음 | `GEOCODE_SIGUNGU_UNVERIFIABLE` |

자치구를 읽을 수 없는 응답은 통과가 아니라 검토 대상입니다. 추측해서 메우지
않습니다. 거부 사유는 버리지 않고 `location_review`에 남겨서, "좌표가 없음"과
"좌표가 틀려서 뺐음"이 보고서에서 구분됩니다. 채택된 좌표는 `location_sigungu`에
응답이 말한 자치구를 함께 남깁니다.

## 6. 기존 데이터 회귀

`seoul-identity-v1`은 그대로입니다. identity 규칙(`cleanup:<external_id>` 또는
`<source_id>:<district>:<name>`)을 건드리지 않았습니다.

확인한 것:

1. **변경 전 파서와 변경 후 파서의 출력이 같습니다.** 캡처된 공식 근거 183건을
   HEAD(변경 전) 코드와 변경 후 코드(범위를 서울 25개로 넓힌 상태)에 각각 통과시켜
   비교했습니다. project_id 집합 동일, 필드 차이 **0건**.
2. **적재된 130건 전부가 지금 코드로 다시 생성됩니다.** `lifecycle_audit_20260929`의
   130개 project_id가 모두 재생된 id 집합 안에 있습니다(차집합 0).
   서초 56 / 강동 40 / 송파 34도 그대로입니다.
3. **범위를 넓혀도 id가 바뀌지 않습니다.** 같은 행을 `--district 강동구`로 만든
   source와 `--all-seoul`로 만든 source에 통과시킨 결과가 project_id·source_url·
   content_hash까지 같습니다. source id(`cleanup_11740`)와 URL이 범위와 무관하게
   같기 때문입니다 — identity에 들어가는 값이 그대로라는 뜻입니다.
4. **기존 세 구의 기본 동작이 그대로입니다.** 인자 없는 `SOURCES`는 id·URL·이름·순서가
   변경 전과 같고, `SOURCES[-1]`은 여전히 서초구 directory source입니다.

즉 기존 데이터가 중복 프로젝트로 다시 만들어지는 경로는 없습니다. 재적재 시 130건은
insert가 아니라 update로 분류됩니다(위 표의 update 열).

## 7. UI 빈 화면

빈 화면에는 서로 다른 세 가지 사정이 있고, 셋 다 다른 문구입니다.

| 상황 | 화면 |
|---|---|
| 조회 실패 (네트워크·예외) | 빨강 — "서버에 연결하지 못했어요" |
| 응답이 ok가 아님 | 주황 — "개발정보를 지금 불러올 수 없어요" |
| 조회 정상, 그 자치구 등록 0건 | `data-state="region-no-data"` — "현재 ○○구의 개발정보를 준비 중입니다." + 지금 볼 수 있는 자치구 안내 |
| 조회 정상, 필터가 다 걸러냄 | `data-state="filtered-empty"` — "유형·진행단계·검색어를 바꿔 보세요" |

"0건"은 응답을 정상으로 받은 뒤에만 말합니다(`noDataForRegion = ready && ...`).
조회가 실패하면 `setReady(false)`로 내려서, 실패가 "준비 중"으로 보이지 않습니다.

## 8. 경기·전국 확장은 하지 않았습니다 — 영향 요인만

이번 변경으로 경기 수집이 가능해지지 않습니다. `normalize_districts`가 서울 외
이름을 거부합니다. 나중에 확장할 때 걸릴 것들:

1. **수집원이 다릅니다.** 정보몽땅(`cleanup.seoul.go.kr`)은 서울시 전용입니다. 경기는
   시·군별 또는 경기도 포털로 출처가 흩어지고, 표 구성과 단계 용어도 다릅니다.
   `parse_page`의 열 위치 가정(`pos+1`~`pos+5`)이 그대로 통하지 않습니다.
2. **코드 체계는 같지만 자리수 전제가 깨집니다.** `REGION_LAWD`의 경기 44개도 같은
   행정표준코드 5자리지만 `11xxx` 전제와 "구로 끝난다"는 전제가 깨집니다
   (`하남시`, `수원시 장안구`처럼 2단계 이름이 있습니다). 행 필터의 자치구 토큰
   매칭을 다시 설계해야 합니다.
3. **bbox가 다릅니다.** 지금 좌표 검증은 서울 bbox + 자치구 일치입니다. 경기는
   bbox를 시·군 단위로 따로 갖거나 공식 경계로 판정해야 합니다.
4. **identity 버전이 필요합니다.** 지금 identity는 `<source_id>:<district>:<name>`
   입니다. 다른 출처가 들어오면 `source_id`가 달라져 같은 사업이 다른 id를 받습니다.
   `seoul-identity-v1`은 FROZEN이므로 새 버전과 매핑 마이그레이션이 필요합니다.
5. **지역 선택 UI의 분모가 바뀝니다.** `MAX_DISTRICTS = 5`, `MAX_CARDS = 200`,
   `development_map`의 `limit=500`이 69개 지역 기준에서는 다시 계산되어야 합니다.
6. **단계 용어 사전.** `services/development_official.STAGE_MAP`은 서울시 단계명
   기준입니다. 다른 지자체 용어를 추측해서 매핑하면 안 됩니다.
